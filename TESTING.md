# Тестирование BlindNav

## 1. Автоматические тесты (без платы)

Всё, что не зависит от RKNN NPU / камеры / аудио-железа / GPS, покрыто
юнит-тестами и гоняется на обычной машине разработки.

### C++ — чистая логика (decode.cpp, threat_logic.cpp)

Без зависимостей от OpenCV/RKNN — только STL.

```bash
cd blind_nav
mkdir -p build && cd build
cmake -DBUILD_TESTS=ON ..
make blind_nav_tests
ctest --output-on-failure
# или напрямую:
./blind_nav_tests
```

Покрывает: IoU/NMS, полный пайплайн decode() (сигмоида → DFL → масштабирование
→ отбрасывание рамок, не поместившихся в кадр целиком), формулу (3) TTC,
формулу (4) интегральной угрозы, вспомогательные таблицы классов/дистанций.

Слово «клиппинг» здесь стояло раньше и вводило в заблуждение: decode() рамку у
края кадра **не обрезает, а выбрасывает целиком** (decode.cpp, фильтр «бокс
внутри кадра»; счётчик отброшенных — параметр `dropped_out`). Теряются при этом
как раз близкие объекты, у которых рамка упирается в край, — то есть самые
опасные. Это известное поведение, менять его без перезамера порогов нельзя, но
называть его обрезкой не следует.

### Python — voice_nav_daemon.py

Модули `vosk`, `gps` и `requests` не устанавливаются на машине разработки —
тесты сами подставляют заглушки перед импортом демона, pytest не требуется:

```bash
cd python
python3 -m unittest discover -s tests -v
```

Покрывает: разбор голосового адреса (`normalize_text`, `find_coordinates`),
нечёткое сравнение с порогом `ADDRESS_MATCH_CUTOFF`, ротацию лог-файлов,
безопасность запуска озвучки в `speak()` (текст из STT уходит отдельным
аргументом `execvp`, оболочки в цепочке нет вовсе), различение
«прозвучало / не прозвучало» по коду возврата say.sh, совпадение констант,
продублированных между python и shell (`HEADSET_RATE`, `AUDIO_LOCK`),
совпадение кэшируемых фраз с тем, что демон действительно произносит, все
ветки `navigation_worker` (не распознано / адрес не найден / отказ на
подтверждении / нет GPS / прибытие) с замоканными STT/TTS/GPS/OSRM.

Эти тесты уже один раз окупились: они поймали реальный баг в
`confirm_address()` — сравнение подстрокой `"да" in answer.lower()` ложно
срабатывало на словах вроде "туда", "погода", т.е. отказ от маршрута мог быть
принят за подтверждение. Исправлено на сравнение целыми словами.

Но какое-то время они не окупались вовсе: в заглушках не хватало `requests`, и
весь набор падал на `ModuleNotFoundError` ещё до первого теста — про запуск при
этом было написано ровно то, что написано выше. Пока набор молчал, в нём
успели протухнуть три вещи: тест звал `direction_to_russian` у демона, откуда
функция переехала в `phrases.py`; сторож безопасности `speak()` проверял
`flock -c`, хотя `speak()` давно перешёл на argv-список без оболочки (то есть
сторож стал красным ровно на той правке, которую охранял); восемь сценарных
тестов по-настоящему запускали `play_ready_tone()`, а он шёл в `flock`/`ffmpeg`
/`pactl` — на плате это молча играло сигнал в живую гарнитуру и крутило
громкость синка посреди прогона тестов. Всё это исправлено; **если набор
перестал запускаться — это отказ, а не мелочь.**

### Чего эти тесты НЕ проверяют

Инференс модели на NPU, реальный захват кадра с камеры, воспроизведение и
запись звука, Bluetooth, GPIO-кнопку, gpsd, OSRM-сервер как процесс — всё это
требует физической платы и не имитируется. Ниже — чек-лист для неё.

### Реальный инференс на NPU без камеры — `rknn_image_test`

Если плата подключена, но без камеры (например, для точечной проверки самой
модели), `blind_nav` целиком не запустить — он читает кадры только с
`cv::VideoCapture`. Для этого случая есть отдельный тестовый бинарник,
который прогоняет `yolo11_final.rknn` на статичных фото через тот же боевой
код (`rknn_inference.cpp` + `decode.cpp`), что использует основной бинарник:

```bash
cd blind_nav && mkdir -p build && cd build
cmake -DBUILD_IMAGE_TEST=ON ..
make rknn_image_test
./rknn_image_test ../model/yolo11_final.rknn ../tests/rgb_bug_demo/street1_correct.jpg ...
```

Печатает список детекций (класс/уверенность/дистанция) и сохраняет
`<фото>_detected.jpg` с отрисованными боксами рядом с исходником. Сравнить
результат можно с `blind_nav/tests/rgb_bug_demo/*_correct.jpg` — та же
модель, но прогнанная через `weights/best.onnx` на PC (`onnxruntime`, без
NPU). Совпадение классов и расположения объектов на одних и тех же фото —
прямое подтверждение, что `yolo11_final.rknn` и `best.onnx` дают согласованный
результат на реальном железе, а не только на синтетических тензорах.

### Замер реального FPS на видео — `rknn_video_bench`

`rknn_image_test` проверяет только корректность (один кадр — один результат),
но не скорость: инференс на одном статичном фото не показывает, сколько FPS
выдаёт NPU на потоке кадров. Для этого — `rknn_video_bench`: гоняет боевой
`RKNNModel::infer()` + `decode()` по всем кадрам видеофайла подряд (без
ограничения частоты) и печатает средний FPS и разбивку времени кадра по
стадиям (препроцессинг / копирование в NPU / сам инференс / деквантование /
decode()).

```bash
cd blind_nav/build
cmake -DBUILD_VIDEO_BENCH=ON ..
make rknn_video_bench
./rknn_video_bench ../model/yolo11_final.rknn ../tests/rgb_bug_demo/pov_walk.mp4
```

`pov_walk.mp4` — уличное видео от первого лица (720p, источник:
[mixkit.co/free-stock-video/footsteps-of-a-young-man-walking-down-the-street-4893](https://mixkit.co/free-stock-video/footsteps-of-a-young-man-walking-down-the-street-4893/),
бесплатная лицензия без атрибуции), лежит в репозитории специально для
воспроизводимого прогона на плате без камеры.

#### Результат прогона на плате (13.08.2026, Orange Pi RK3566, `yolo11_final.rknn`)

161 кадр, 1280×720 источник (масштабируется до 512×512 внутри `infer()`):

- **Средний FPS: 10.45** (9.71 с учётом чтения видеофайла) — совпадает по
  порядку величины с ~8 FPS, которые ранее наблюдались вживую с камерой
  (разница объяснима декодированием видео на CPU и другой сценой).
- Разбивка среднего кадра (95.7 мс):

  | Стадия | мс | % |
  | :--- | ---: | ---: |
  | resize+cvtColor (препроцессинг, CPU) | 6.12 | 6% |
  | `rknn_inputs_set` (копирование в буфер NPU) | 25.75 | **27%** |
  | `rknn_run` (сам инференс на NPU) | 56.85 | **59%** |
  | `rknn_outputs_get` (деквантование, CPU) | 2.73 | 3% |
  | `decode()` (sigmoid+DFL+NMS, CPU) | 3.59 | 4% |

**Вывод (обновлён 14.08.2026, см. [METRICS.md](METRICS.md)).** 59% времени —
это сам инференс на NPU, нижняя граница без изменения модели. Оставшиеся 27%
в `rknn_inputs_set` выглядели как лишнее копирование 786 КБ, но это оказалось
не так:

1. ~~**Zero-copy вход** даст ~14 FPS вместо 10.4.~~ **Проверено и опровергнуто
   замером.** Zero-copy реализован (`rknn_create_mem` + `rknn_set_io_mem`,
   включается через `BLIND_NAV_NO_ZERO_COPY=0`), передача входа падает с
   25.6 мс до 0.24 мс — но `rknn_run` ровно на столько же вырастает (56 → 88 мс),
   итог 9.75 FPS против 10.56, то есть хуже. Причина: `yolo11_final.rknn` имеет
   **FP16-вход** (модель не квантована), и те 25 мс — не копирование, а
   конверсия uint8 → fp16, которую всё равно кто-то обязан выполнить.
   Реальный резерв скорости — квантование модели в INT8, а не оптимизация
   конвейера; подробности и замеры в [METRICS.md](METRICS.md).
2. **Перекрытие CPU-препроцессинга кадра N+1 с `rknn_run` кадра N** (два
   потока вместо одного): `rknn_run` блокирующий, 56.85 мс NPU занят, а CPU
   всё это время простаивает — можно готовить следующий кадр в этот момент.
   Даёт меньше, чем п.1 (препроцессинг всего 6 мс), но не требует новых
   зависимостей — актуально делать после п.1.
3. **RGA (аппаратный 2D-блок RK3566) вместо `cv::resize`/`cv::cvtColor`** —
   снимет 6 мс CPU-нагрузки, но при уже сделанном п.2 прямого прироста FPS
   не даст (эти 6 мс и так спрячутся под NPU), скорее освобождает CPU для
   потока камеры/кнопки/трекинга при высокой нагрузке.
4. **Квантование модели в INT8** — главный резерв. Сейчас NPU считает модель
   в FP16 (проверено `rknn_query`: вход и все выходы `type=FP16`, `scale=1.0`),
   хотя RK3566 заточен под INT8. Это же снимет и конверсию входа, после чего
   zero-copy из п.1 начнёт приносить пользу. Цена — падение точности, которое
   измеряется на той же валидационной выборке ([METRICS.md](METRICS.md)).

Ни один из пунктов 1-3 не меняет точность (тот же вход, тот же INT8-выход) —
это чисто инженерная оптимизация конвейера, а не компромисс с качеством.

## 2. Ручная проверка на плате (Orange Pi)

Прогонять после каждого разворачивания на плате и перед выставкой.

### Зрение / NPU
- [ ] `blind_nav` стартует и держит устойчивый FPS (см. вывод "Инференс: N ms" в консоли/журнале).
- [ ] Модель `blind_nav/model/yolo11_int8.rknn` (та, что в `MODEL_PATH`) грузится без ошибок `rknn_init`.
- [ ] Детекция человека/машины/светофора визуально совпадает с реальной сценой (особенно после правки RGB/BGR — сверить, что цветовые классы, например светофор, распознаются увереннее, чем раньше).
- [ ] Отключить/перекрыть камеру на 5+ секунд — убедиться, что видно сообщение о переоткрытии устройства и поток восстанавливается.
- [ ] **Закрыть объектив ладонью на 5+ секунд** — устройство должно вслух сказать "Камера не видит", написать в журнал "картинки в них нет" и повторять сообщение раз в полминуты, пока объектив закрыт; после того как ладонь убрали — сказать "Камера снова видит". Это проверка отказа 19.08.2026, при котором камера продолжала отдавать кадры с нормальным темпом, но все они были равномерно чёрными: прежняя проверка `temp_frame.empty()` его не видела, и устройство молча не предупреждало о препятствиях 7 минут 44 секунды. Ладонь имитирует его достаточно точно — важно, что кадры при этом идут.
- [x] **Порог `CAMERA_BLANK_STDDEV = 1.5` проверен на плате 22.08.2026 с обеих сторон.** Ладонь на объективе — сторож срабатывает и отпускает: четыре цикла «камера ослепла» → переоткрытие → «картинка вернулась» за пять минут, каждый длиной 3-8 секунд, ложных срабатываний между ними нет. Выключенный свет в комнате (в кадре ещё различимы потолок и люстра) сторож не трогает, и это правильно: кадр тёмный, но не пустой, детектор на нём работает. Для масштаба: у нормально освещённого кадра среднеквадратичное отклонение по превью 32x24 равно 57.9 — от порога это тридцать восемь крат. Тревожиться стоит, если сторож начнёт срабатывать без ладони: значит, порог задран.
- [ ] Убедиться, что фразы "Камера не видит" и "Камера снова видит" звучат **мгновенно**, а не через пять секунд: значит, они попали в кэш озвучки. Если задержка есть — прогнать `tools/build_voice_cache.sh` (список фраз он берёт из `voice_phrases`, куда они добавлены).
- [ ] Держать объектив закрытым дольше минуты — в журнале должны появиться попытки переоткрытия, а после двух неудачных подряд — "Ресет USB-порта 5-1". Микрофон вебкамеры при ресете отваливается; проверить, что `record_session.sh` поднял его заново ("запись микрофона оборвалась — поднимаю заново") и `ambient_<тег>.mp3` продолжил расти.
- [ ] Голосовое предупреждение об опасном объекте звучит с адекватной задержкой и не дублируется.

### Аудио / Bluetooth
- [ ] `bt_keeper.service` переподключает наушники после разрыва без падения звука в остальных процессах.
- [ ] Предупреждение об опасности (C++) и голос маршрута (Python) не звучат одновременно поверх друг друга (проверка `flock` на `/run/lock/blind_nav_audio.lock`).
- [ ] `system_audio.raw`/`mic_audio.raw` не растут неограниченно (проверить размер после длительного прогона, должен упираться в 20 МБ и сбрасываться).
- [ ] **Отказ озвучки виден.** Выключить гарнитуру посреди прогулки и дождаться предупреждения: в журнале должны появиться строки «aplay отказал … пробую default» и, если и там не вышло, «ФРАЗА НЕ ПРОЗВУЧАЛА». Молчаливого отказа быть не должно — раньше `aplay` запускался с `2>/dev/null` и без проверки кода, и непрозвучавшее предупреждение выглядело в `speech.tsv` как прозвучавшее.
- [ ] **`speech.tsv` — летопись звука, а не намерений.** После прогулки в файле четыре колонки (метка, файл, текст, фактическая длительность), и записи есть только у тех реплик, которые действительно шли в наушник. У вытесненной предупреждением подсказки маршрута длительность заметно меньше длины файла — это норма, так и должно быть.
- [ ] **Приоритет звука.** `ps -L -o tid,cls,rtprio,ni,comm -p $(pgrep -x pulseaudio)` — у всех потоков должно быть `NI = -11`. Это работающая часть: `--high-priority` применяется, и именно она снимает хруст вместе с убранным покадровым кодированием JPEG.
- [ ] Класса `RR`/`FF` на этой плате не будет ни у одного потока, и это **не** повод чинить. Проверено 22.08.2026: `chrt -r 5 true` под root отвечает `Operation not permitted` — ядро не выдаёт RT-политику никому, ни pulseaudio, ни чему-либо ещё. Лимиты юнита тут ни при чём (`LimitRTPRIO=20` стоит, а в `/proc/<pid>/limits` видно 9 — pulseaudio ставит себе собственный дефолт, и девяти хватило бы). `bt_keeper` пишет об этом спокойной строкой «Планирование в реальном времени этим ядром не выдаётся никому». Если однажды сменят ядро на собранное с RT-политиками, скрипт вместо неё выдаст `ВНИМАНИЕ` — вот тогда рестарт `bt_keeper` осмыслен.
- [ ] **Хруст проверяется прогулкой, а не выводом `ps`.** Нагрузить плату как в бою (запись видео, инференс, GPS) и послушать A2DP пять минут. Первое, что искать при возврате хруста, — новую периодическую работу в цикле кадра, а не настройки планировщика.
- [ ] **Плохой звук в наушниках: причина измерена 23.08.2026, догадки закрыты.** За 4.63 с проигрывания контроллер передал 44731 байт — это **77 кбит/с**. Минимум для SBC 44100 стерео — 229 кбит/с (bitpool 35), обычный режим — 328 (bitpool 53). В наушники уходит треть нужного потока, то есть звук не «иногда рвётся», а постоянно идёт сильно пережатым. Меряется прогоном 1 `tools/audio_dropout_test.sh` по счётчику `TX bytes` самого контроллера; ушей не требует.
- [ ] Узкое место — UART. `hciconfig -a` → `Bus: UART`, драйвер `hci_uart_bcm` на `/serial@fe650000/bluetooth`. Линия 8N1 отдаёт `бод × 0,8`: при 115200 это 92 кбит/с, и измеренные 77 — уже 84% занятости. При этом `max-speed` в device tree **не нашёлся ни в одном узле**, а без него драйвер остаётся на начальной скорости. Когда запись в транспорт начинает отказывать, PulseAudio сам понижает bitpool, чтобы влезть, — ровно наблюдаемая картина. Проверять дампом узла (прогон 1 показывает его целиком) и строками о смене bitpool в журнале сервера.
- [ ] **Что уже исключено и повторять не нужно.** Записи в кэше целые (монтажная дорожка собрана из тех же файлов и звучит чисто). Сервер отдаёт поток в синк целым (монитор совпал с эталоном). Эфир ни при чём: `RSSI -1`, `Link quality 255` — это максимум, и два прогона с выключенным wifi дали тот же счёт. Наушники ни при чём: Marshall Major IV на телефоне играют без нареканий. Буфер не лечит: 68 мс — 0 попыток из 5 чисто, 500 мс — 2 из 5, 1000 мс снова плохо; немонотонность и означает упор в пропускную способность, а не в запас времени.
- [ ] **Кандидат на лечение без правки ядра — HFP вместо A2DP.** Устройство озвучивает только речь, а профиль HFP для речи и сделан: mSBC это 16 кГц моно, около 64 кбит/с — втрое меньше A2DP и помещается в 92 кбит/с целиком. Гарнитура профиль уже умеет, демон переводит её туда на время диктовки. Прогон 2 `audio_dropout_test.sh` проверяет обратное направление — воспроизведение. Оговорка: у части контроллеров Broadcom звук SCO идёт мимо HCI, по PCM/I2S; тогда HFP будет либо идеально чистым, либо не зазвучит вовсе, и то и другое информативно.
- [ ] Если HFP не подходит — поднимать `max-speed` в device tree (типично `<1500000>` для BCM на Rockchip) и пересобирать dtb. Это настоящее лечение, но оно требует перезагрузки и правки загрузчика.
- [ ] **Отдельно от пропускной способности: помехи именно В НАЧАЛЕ фразы.** `module-suspend-on-idle` усыпляет синк, а для bluez сон означает разбор A2DP-транспорта: следующая фраза начинается с переговоров AVDTP, разгона кодера и наполнения пустого буфера — поверх первых долей секунды речи. Для боевого устройства это основной режим: между репликами маршрута проходят минуты, значит **каждая** фраза стартует холодной. Прогон 3 сравнивает холодный старт (синку дают уснуть 12 с) с тёплым (фоном играет тишина из `/dev/zero`). Чистое начало только в тёплом — лечится фоновой тишиной из `bt_keeper`, и делать это стоит независимо от истории с каналом.
- [ ] Замеры на слух записывать счётом «сколько из пяти чисто», а не словами: помехи случайны, и одна попытка на условие — гадание.
