# Тестирование BlindNav

## 1. Автоматические тесты (без платы)

Всё, что не зависит от RKNN NPU / камеры / аудио-железа / GPS, покрыто
юнит-тестами и гоняется на обычной машине разработки.

### C++ — чистая логика (decode.cpp, threat_logic.cpp)

Без зависимостей от OpenCV/RKNN — только STL.

```bash
cd blind_nav
mkdir -p build && cd build
cmake -DBUILD_TESTS=ON ..
make blind_nav_tests
ctest --output-on-failure
# или напрямую:
./blind_nav_tests
```

Покрывает: IoU/NMS, полный пайплайн decode() (сигмоида → DFL → масштабирование
→ клиппинг по границам кадра), формулу (3) TTC, формулу (4) интегральной
угрозы, вспомогательные таблицы классов/дистанций.

### Python — voice_nav_daemon.py

Модули `vosk` и `gps` не устанавливаются на машине разработки — тесты сами
подставляют заглушки перед импортом демона, pytest не требуется:

```bash
cd python
python3 -m unittest discover -s tests -v
```

Покрывает: разбор голосового адреса (`normalize_text`, `find_coordinates`),
нечёткое сравнение с порогом `ADDRESS_MATCH_CUTOFF`, ротацию лог-файлов,
безопасность построения shell-команды в `speak()` (текст из STT не должен
уметь вырваться из `flock -c '...'`), все ветки `navigation_worker`
(не распознано / адрес не найден / отказ на подтверждении / нет GPS /
прибытие) с замоканными STT/TTS/GPS/OSRM.

Эти тесты уже один раз окупились: они поймали реальный баг в
`confirm_address()` — сравнение подстрокой `"да" in answer.lower()` ложно
срабатывало на словах вроде "туда", "погода", т.е. отказ от маршрута мог быть
принят за подтверждение. Исправлено на сравнение целыми словами.

### Чего эти тесты НЕ проверяют

Инференс модели на NPU, реальный захват кадра с камеры, воспроизведение и
запись звука, Bluetooth, GPIO-кнопку, gpsd, OSRM-сервер как процесс — всё это
требует физической платы и не имитируется. Ниже — чек-лист для неё.

### Реальный инференс на NPU без камеры — `rknn_image_test`

Если плата подключена, но без камеры (например, для точечной проверки самой
модели), `blind_nav` целиком не запустить — он читает кадры только с
`cv::VideoCapture`. Для этого случая есть отдельный тестовый бинарник,
который прогоняет `yolo11_final.rknn` на статичных фото через тот же боевой
код (`rknn_inference.cpp` + `decode.cpp`), что использует основной бинарник:

```bash
cd blind_nav && mkdir -p build && cd build
cmake -DBUILD_IMAGE_TEST=ON ..
make rknn_image_test
./rknn_image_test ../model/yolo11_final.rknn ../tests/rgb_bug_demo/street1_correct.jpg ...
```

Печатает список детекций (класс/уверенность/дистанция) и сохраняет
`<фото>_detected.jpg` с отрисованными боксами рядом с исходником. Сравнить
результат можно с `blind_nav/tests/rgb_bug_demo/*_correct.jpg` — та же
модель, но прогнанная через `weights/best.onnx` на PC (`onnxruntime`, без
NPU). Совпадение классов и расположения объектов на одних и тех же фото —
прямое подтверждение, что `yolo11_final.rknn` и `best.onnx` дают согласованный
результат на реальном железе, а не только на синтетических тензорах.

### Замер реального FPS на видео — `rknn_video_bench`

`rknn_image_test` проверяет только корректность (один кадр — один результат),
но не скорость: инференс на одном статичном фото не показывает, сколько FPS
выдаёт NPU на потоке кадров. Для этого — `rknn_video_bench`: гоняет боевой
`RKNNModel::infer()` + `decode()` по всем кадрам видеофайла подряд (без
ограничения частоты) и печатает средний FPS и разбивку времени кадра по
стадиям (препроцессинг / копирование в NPU / сам инференс / деквантование /
decode()).

```bash
cd blind_nav/build
cmake -DBUILD_VIDEO_BENCH=ON ..
make rknn_video_bench
./rknn_video_bench ../model/yolo11_final.rknn ../tests/rgb_bug_demo/pov_walk.mp4
```

`pov_walk.mp4` — уличное видео от первого лица (720p, источник:
[mixkit.co/free-stock-video/footsteps-of-a-young-man-walking-down-the-street-4893](https://mixkit.co/free-stock-video/footsteps-of-a-young-man-walking-down-the-street-4893/),
бесплатная лицензия без атрибуции), лежит в репозитории специально для
воспроизводимого прогона на плате без камеры.

#### Результат прогона на плате (13.08.2026, Orange Pi RK3566, `yolo11_final.rknn`)

161 кадр, 1280×720 источник (масштабируется до 512×512 внутри `infer()`):

- **Средний FPS: 10.45** (9.71 с учётом чтения видеофайла) — совпадает по
  порядку величины с ~8 FPS, которые ранее наблюдались вживую с камерой
  (разница объяснима декодированием видео на CPU и другой сценой).
- Разбивка среднего кадра (95.7 мс):

  | Стадия | мс | % |
  | :--- | ---: | ---: |
  | resize+cvtColor (препроцессинг, CPU) | 6.12 | 6% |
  | `rknn_inputs_set` (копирование в буфер NPU) | 25.75 | **27%** |
  | `rknn_run` (сам инференс на NPU) | 56.85 | **59%** |
  | `rknn_outputs_get` (деквантование, CPU) | 2.73 | 3% |
  | `decode()` (sigmoid+DFL+NMS, CPU) | 3.59 | 4% |

**Вывод (обновлён 14.08.2026, см. [METRICS.md](METRICS.md)).** 59% времени —
это сам инференс на NPU, нижняя граница без изменения модели. Оставшиеся 27%
в `rknn_inputs_set` выглядели как лишнее копирование 786 КБ, но это оказалось
не так:

1. ~~**Zero-copy вход** даст ~14 FPS вместо 10.4.~~ **Проверено и опровергнуто
   замером.** Zero-copy реализован (`rknn_create_mem` + `rknn_set_io_mem`,
   включается через `BLIND_NAV_NO_ZERO_COPY=0`), передача входа падает с
   25.6 мс до 0.24 мс — но `rknn_run` ровно на столько же вырастает (56 → 88 мс),
   итог 9.75 FPS против 10.56, то есть хуже. Причина: `yolo11_final.rknn` имеет
   **FP16-вход** (модель не квантована), и те 25 мс — не копирование, а
   конверсия uint8 → fp16, которую всё равно кто-то обязан выполнить.
   Реальный резерв скорости — квантование модели в INT8, а не оптимизация
   конвейера; подробности и замеры в [METRICS.md](METRICS.md).
2. **Перекрытие CPU-препроцессинга кадра N+1 с `rknn_run` кадра N** (два
   потока вместо одного): `rknn_run` блокирующий, 56.85 мс NPU занят, а CPU
   всё это время простаивает — можно готовить следующий кадр в этот момент.
   Даёт меньше, чем п.1 (препроцессинг всего 6 мс), но не требует новых
   зависимостей — актуально делать после п.1.
3. **RGA (аппаратный 2D-блок RK3566) вместо `cv::resize`/`cv::cvtColor`** —
   снимет 6 мс CPU-нагрузки, но при уже сделанном п.2 прямого прироста FPS
   не даст (эти 6 мс и так спрячутся под NPU), скорее освобождает CPU для
   потока камеры/кнопки/трекинга при высокой нагрузке.
4. **Квантование модели в INT8** — главный резерв. Сейчас NPU считает модель
   в FP16 (проверено `rknn_query`: вход и все выходы `type=FP16`, `scale=1.0`),
   хотя RK3566 заточен под INT8. Это же снимет и конверсию входа, после чего
   zero-copy из п.1 начнёт приносить пользу. Цена — падение точности, которое
   измеряется на той же валидационной выборке ([METRICS.md](METRICS.md)).

Ни один из пунктов 1-3 не меняет точность (тот же вход, тот же INT8-выход) —
это чисто инженерная оптимизация конвейера, а не компромисс с качеством.

## 2. Ручная проверка на плате (Orange Pi)

Прогонять после каждого разворачивания на плате и перед выставкой.

### Зрение / NPU
- [ ] `blind_nav` стартует и держит устойчивый FPS (см. вывод "Инференс: N ms" в консоли/журнале).
- [ ] Модель `blind_nav/model/yolo11_int8.rknn` (та, что в `MODEL_PATH`) грузится без ошибок `rknn_init`.
- [ ] Детекция человека/машины/светофора визуально совпадает с реальной сценой (особенно после правки RGB/BGR — сверить, что цветовые классы, например светофор, распознаются увереннее, чем раньше).
- [ ] Отключить/перекрыть камеру на 5+ секунд — убедиться, что видно сообщение о переоткрытии устройства и поток восстанавливается.
- [ ] Голосовое предупреждение об опасном объекте звучит с адекватной задержкой и не дублируется.

### Аудио / Bluetooth
- [ ] `bt_keeper.service` переподключает наушники после разрыва без падения звука в остальных процессах.
- [ ] Предупреждение об опасности (C++) и голос маршрута (Python) не звучат одновременно поверх друг друга (проверка `flock` на `/run/lock/blind_nav_audio.lock`).
- [ ] `system_audio.raw`/`mic_audio.raw` не растут неограниченно (проверить размер после длительного прогона, должен упираться в 20 МБ и сбрасываться).

### Кнопка / навигация
- [ ] Короткое нажатие кнопки запускает `navigation_worker`, долгий разговор не блокирует поток кнопки.
- [ ] Повторное нажатие во время активного маршрута отменяет его ("ОТМЕНА МАРШРУТА").
- [ ] `/dev/shm/nav_active` синхронно меняется с реальным статусом навигации. Это диагностический признак: предупреждения об опасности звучат всегда, в том числе посреди маршрута, и от этого файла не зависят.
- [ ] Во время диктовки адреса (`/dev/shm/nav_mic_open` = 1) предупреждение откладывается, но звучит сразу после закрытия микрофона — а не пропадает совсем.
- [ ] Подтверждение адреса ("Вы имели в виду...? Да/нет") корректно распознаёт и "да", и явный отказ ("нет", "не туда") — см. исправленный баг выше.

### GPS / маршрутизация
- [ ] `get_current_location()` возвращает координаты в разумное время (на улице, с чистым небом).
- [ ] OSRM-сервер (`osrm-routed`) поднят и отвечает на `127.0.0.1:5000`; при его падении демон не молчит, а периодически предупреждает голосом (`OSRM_FAILURE_WARN_EVERY`).
- [ ] Пошаговые инструкции ("через N метров налево/направо") звучат вовремя и не повторяются на одном и том же манёвре.

### Отказоустойчивость системы
- [ ] `systemctl status blind_nav_main bt_keeper nav_daemon nav_record` — все `active (running)`, без рестарт-шторма (`RestartSec`/`StartLimitBurst` не срабатывают в норме).
- [ ] Принудительно убить каждый процесс (`kill`) — сервис поднимается сам в течение нескольких секунд.
- [ ] Запись прогулки (`videos/capture_<тег>.avi`) режется по 500 МБ и не съедает всю SD-карту за время выставки; при остатке меньше 2 ГБ запись видео должна приостановиться и сама возобновиться, когда монтаж освободит место.
- [ ] После остановки `blind_nav_main.service` в `videos/` появляются `full_video_<тег>.mp4` с рамками, голосом модели и голосом человека.
- [ ] `bash tools/mic_check.sh` до съёмки даёт вердикт «сигнал есть» хотя бы по одному микрофону.
- [ ] Второй выход в тот же день после автомонтажа пишется в свой тег (`19_08_2026_2`), а не поверх уже готового `full_video_19_08_2026.mp4`.
- [ ] Срыв питания посреди прогулки: после включения `nav_record` сам домонтирует оборванную запись (в журнале — «meta повреждена — восстанавливаю по самой записи»), а не бросает её сотней мегабайт на карте.
- [ ] После подачи питания (без ssh-входа) в журнале `bt_keeper` есть обе строки — `auto_switch=false` и `module-suspend-on-idle выгружен`: без них профиль уводит в A2DP и начало фраз срезается.
- [ ] Кэш озвучки собран (`ls piper/cache | wc -l` — сотни файлов): предупреждение должно звучать сразу, а не через пять секунд.
- [ ] Предупреждение об опасности обрывает звучащую подсказку маршрута, а не встаёт за ней в очередь.
- [ ] `df -h` перед стартом и после нескольких часов работы — свободное место не падает подозрительно быстро.
