# Демонстрация бага RGB/BGR на реальной модели

Прогон `weights/best.onnx` (те же веса, что и в `yolo11_final.rknn`, но в
FP32 и без конвертации в RKNN) через `onnxruntime` на трёх фото — сравнение
правильного препроцессинга (одна конвертация BGR→RGB) со старым багом
(двойная конвертация BGR→RGB→BGR, воспроизводит то, что реально уходило на
NPU до исправления в `main.cpp`).

Скрипт: `run_inference.py` (требует `onnxruntime`, `opencv-python`, `numpy` —
не входят в зависимости проекта, только для этой разовой проверки).

- `street1_*`, `street2_aug_*` — фото из датасета (уже лежали в blind_nav/).
- `video_frame*` — кадр №150 из `13307997_2560_1440_30fps.mp4`.
- `*_correct.jpg` — с правильной (текущей) конвертацией цвета.
- `*_buggy.jpg` — с воспроизведённым старым багом.

Итог: под багом пропадает часть детекций (иногда в 3-5 раз меньше объектов),
на video_frame полностью пропадает светофор. Подробности — в переписке с
Claude Code (эта проверка не подтверждает decode.cpp побайтово, т.к. ONNX
и RKNN-модель отдают выход в разном формате — decode.cpp отдельно покрыт
юнит-тестами на синтетических тензорах, см. blind_nav/tests/test_logic.cpp).

## npu_real/ — тот же прогон, но на настоящем NPU (Orange Pi, RK3566)

13.08.2026 подключили голую плату (без камеры) по SSH, собрали на ней
`blind_nav/tests/rknn_image_test.cpp` (боевой `rknn_inference.cpp` +
`decode.cpp`, без синтетики) и прогнали `yolo11_final.rknn` на тех же трёх
исходных фото (`street1`, `street2_aug`, `video_frame.jpg`) через реальный
NPU. Результат в `npu_real/*_npu_detected.jpg`.

Сравнение с `best.onnx` (FP32, на PC) по всем трём фото — 27 детекций
суммарно:
- классы, координаты боксов и дистанции совпадают у подавляющего
  большинства детекций с точностью до 1-2 пикселей и пары процентов
  уверенности;
- часть детекций на PC пропала на NPU из-за более высокого порога
  уверенности в C++ (`CONF_THRESHOLD = 0.30`, у ONNX-скрипта `0.25`) —
  ожидаемо, не расхождение весов;
- одна детекция (мелкий бордюр на video_frame, conf≈0.42 на PC) не
  прошла порог на NPU — типичный шум INT8-квантования на границе
  уверенности, не системная ошибка;
- совпадение такого качества по 27 независимым боксам практически
  исключает вариант "разные веса" — так не совпадает FP32-модель с
  INT8-моделью, обученной на других данных.

Это делает вопрос "best.onnx и yolo11_final.rknn — веса одной модели?"
закрытым: подтверждено прямым запуском на реальном железе, а не только
по метаданным файла.
